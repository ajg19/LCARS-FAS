What is FAS?

FAS (For All Species) brings together open data about space from sources that were never designed to work together: the NORAD satellite catalogue (via Space-Track), CelesTrak, Jonathan McDowell's General Catalog of Artificial Space Objects (GCAT), SatNOGS, Launch Library 2 and space news feeds. For space weather it adds NOAA’s Space Weather Prediction Center, NASA’s DONKI database, GFZ Potsdam, the University of Bern, the Oulu cosmic ray station and SILSO: solar wind, flares, storms, aurorae, the ionosphere and cosmic rays, from spacecraft at L1 to ground-based networks.

Each source answers part of a question. Combined, the whole is greater than the sum of its parts: matched object by object, reconciled and charted in one place, they answer questions none of them can answer alone. Who owns what is in orbit? Where is the debris, and what did it break off? Which satellites can a ground station hear? What is the Sun doing, and what will it do to satellites, radio links and the aurora? How is all of it changing?

FAS is a not-for-profit project, offered freely in the same spirit in which Tim Berners-Lee gave the World Wide Web away and Linus Torvalds released Linux. We hope it will be useful in education: for students, teachers and anyone curious about what is up there, who put it there and what it is doing.

The data refreshes automatically; the table on the landing page shows when each source last updated. The site is built to stay usable at 20 Mbps with multi-second latency, so it works from anywhere, from a classroom on a slow connection to the ISS.

What it covers
  • On orbit: every catalogued object (payloads, rocket bodies and debris) by orbit, owner, country, sector, mission, manufacturer and radio band, with debris history and origins.
  • Ground tracks: live positions, ground tracks and footprints for any catalogued object, computed in the browser.
  • Ground station operations: the satellites in view from any location, with link-budget estimates in both directions.
  • Launches: orbital launches since 1957 by year, country and outcome, and the payloads they carried.
  • Space weather: what the Sun is sending (solar wind, flares, coronal mass ejections), its effect at Earth (geomagnetic storms, the auroral oval, drag on low orbits, satellite and HF radio links) and galactic cosmic rays, combining NOAA SWPC, NASA DONKI, GFZ Potsdam, the CODE ionosphere maps, the Oulu neutron monitors and SILSO, with live images of the Sun. Each chart names the spacecraft behind it, where it is and how far away, in light-seconds.
  • Ground segment and news: a map of ground infrastructure (deep-space networks, teleports, SSA sites, launch sites) and a categorised space-news feed.

How FAS was built
Data pipeline
Scheduled scripts on the server fetch each source and store it in its own SQLite database. Orbital elements for the NORAD catalogue (from Space-Track and CelesTrak, OMM JSON) are fetched twice a day, the NORAD satellite catalogue (SATCAT) daily, GCAT weekly and news every 30 minutes. Radio-frequency data from SatNOGS and estimated transmit power are added after each orbital refresh. Derived statistics are recomputed after every refresh, so charts are counted on request from current data.
Combining sources
Objects are matched across sources by NORAD catalogue number. GCAT supplies ownership, sector, mission and manufacturer; CelesTrak's active list supplies operational status. Where a value is estimated rather than published (transmit power, and most satellites' downlink band), it is marked as an estimate. Each section's DEFS page gives its definitions and how its numbers are counted.
Low-bandwidth design
Required to stay usable at 20 Mbps with multi-second latency (for example, from the ISS via NASA's optical links). Plain JavaScript with no framework; one module per section, loaded only when opened; self-hosted libraries, no third-party CDNs; an initial load under 5 MB. Orbits are propagated (SGP4) in the browser, not on the server.
Space weather
Scheduled scripts fetch each space-weather source into its own database and publish them together into one site file. The 1-minute solar wind and X-ray series are kept for 90 days and then deleted; the indices, events and forecasts are kept longer. Each chart says which spacecraft or network supplied its data, where that spacecraft is, and how far from Earth in light-seconds.
Derived quantities
FAS computes some quantities itself from the stored data: the solar wind coupling indicators (the product of speed and southward field, and the Newell coupling function), the equatorward edge of the auroral oval from the OVATION map, daily flare maxima and storm lists. The tooltip on each chart gives the formula and its limits.
Models and observations
OVATION, D-RAP, GloTEC and the CODE predictions are model output, not direct observations, and are labelled as such. Forecast values are drawn hatched or dashed, with the time they were issued. Values still awaiting confirmation (Dst, Kp, sunspot number) are marked provisional.
Visit counting
Once per browser session the page tells the server it was opened. The server looks the visitor’s internet address up in a city table in memory, adds one to that city’s count for the day, and discards the address; FAS never writes it to its databases or logs. Only the day, city, country and approximate position are kept. (The web host keeps its own server logs, which FAS does not control.)
Server
A single small Python web application serving the page and its data API, on ordinary shared hosting. It serves only the page and its assets, never the databases or scripts.
Process
A hybrid method. Traditional engineering where the requirements are clear: functional and software requirements, a design and architecture document, and a test plan. Agile iteration where they are not, with exploratory prototypes, and a working system at all times. An automated test suite, a bug log, and version control throughout.
Built with AI
Developed by Al Gill with Claude (Anthropic) as development partner. Al set the direction and requirements and tested the results; Claude co-wrote the design documents and implemented and tested the code.
How visits are counted

Each circle is a city; its area is proportional to the number of visits from there. A visit is counted once per browser session, by city only: the visitor’s internet address is looked up in memory and then discarded, so FAS stores and shares no address. Searches by automated programs are not counted, and a visitor using a VPN or a mobile network may appear in another city. The lookup uses IP Geolocation by DB-IP (CC‑BY‑4.0).
